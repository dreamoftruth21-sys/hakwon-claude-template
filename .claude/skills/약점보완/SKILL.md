# 약점 보완 자료 · 약점 확인 시험

빌더는 `공용/build/약점보완/` (형식은 그 `README.md`). **스크립트를 새로 짜지 않는다** — 반 작업폴더에 설정·응시기록·학생별 설명 파일만 만든다.
완성 예시 파일은 이 템플릿에 없다 — 형식은 `공용/build/약점보완/README.md` 의 설정.json · 응시기록.json · 학생_<이름>.py 표를 따른다. 첫 학생 자료를 선생님이 승인하면 그 파일을 다음 학생의 기준으로 쓴다.

## 0. 조건 확인
- 반이 푼 실전 모의고사 회차가 **공용 모의고사 빌더 형식 data.json** 으로 있는가 (옛 스크립트 회차는 `공용/build/모의고사/옛py변환.py`)
- 학생 답: 온라인 회차는 구글 시트 「온라인채점」, 종이 회차는 틀린 번호(사용자에게 받는다). **종이 회차는 고른 답이 없다.**
- 없으면 만들지 말고 무엇이 없는지 말한다.

## 1. 응시 기록 모으기 → `작업/개인패키지/응시기록.json`
- 시트 `제출` 탭: 드라이브 커넥터 `download_file_content`(xlsx 내보내기)로 **실시간** 시트를 받는다. `read_file_content` 는 검색용 사본이라 몇십 분 늦다 — 쓰지 않는다 (방법은 빌더 README 응시기록 절). 학생·시험마다 **첫 제출** 입력 답만 쓴다 (재제출은 답을 바꿔 본 것이다).
- 범위 밖 문항(예: Read More)은 `exclude`. 학생이 말한 입력 실수는 `corrections` 에 적고 `ans` 는 고친다 — 시트 원본은 건드리지 않는다.
- 아직 안 낸 회차는 넣지 않는다 (빌더가 통계·연습 문제에서 뺀다).

## 2. 분석 → 약점 묶기 (사용자와 먼저 맞춘다)
- 학생마다 유형별 **틀린 수 / 푼 수** (`build.kind` 기준). 비율이 높은 유형부터 약점 3~6개로 묶는다. 한두 문항뿐인 유형은 비슷한 유형과 묶는다.
- 구성은 처음 한 번 사용자에게 보여 주고 정한다. 사례로 정한 구성: 표지(회차별 결과 · 유형별 오답 개수 · 약점 · 목차 · 푸는 순서) → 약점마다 [틀린 문제 · 원인 · 보완 방법 · 예제 풀이 · 다시 풀기 · 연습 문제] → 답지 따로.

## 3. 한 명 먼저 → 피드백 → 나머지
- **한 명을 먼저 완성해 보여 준다.** 사용자 지적을 반영한 뒤 나머지를 만든다.
- 나머지는 학생마다 에이전트에 초안을 맡겨도 된다 (병렬). 프롬프트에 아래 4절 규칙 전부와 기준 파일 경로를 넣는다. 쓰는 파일은 `학생_<이름>.py` 하나로 제한한다.
- **초안은 반드시 검토한다** — 문항 3~5개를 골라 고른 답 · 정답 · 지문을 직접 대조한다. 데이터로 확인할 수 없는 단정(22번에서 "어느 밑줄을 틀렸다")은 사실만 남게 고친다.

## 4. 설명 글 규칙 (사용자 지적 모음 — 어기면 다시 쓰게 된다)
1. **당연한 말 금지.** "맞는 밑줄을 틀렸다고 보거나 틀린 밑줄을 맞다고 넘긴다", "(A)가 틀리고 (B)는 맞았다"처럼 정보 없는 말을 쓰지 않는다. **어떤 어법 · 어떤 단어 · 어떤 내용**인지 실제 문항 예로 쓴다.
2. **추상적 요약 금지.** "단어 한두 개만 바뀌어 있을 때 놓친다"가 아니라 지문 원문과 선택지를 나란히 보여 준다 (sometimes → "언제나").
3. 원인은 데이터로 뒷받침되는 것만. 요약·어휘는 **정답 단어를 몰랐는지 / 쉬운 단어인데 설명 대상을 잘못 잡았는지**를 가른다. 22번은 고른 개수만 있으니 "틀린 밑줄(…) 가운데 적어도 N개를 O 로 판단"까지만.
4. 모호한 말 금지: "틀린 단어로 고른다" → "문맥에 맞게 쓰인 어려운 단어 X를 문맥에 맞지 않는 단어로 골랐다".
5. 표현: **"틀린 것처럼 느껴지지만 옳은 어법" / "옳은 것처럼 느껴지지만 틀린 어법"** ("틀려 보이는 맞는 밑줄" 금지). "모양", 어색한 비유, 주어 **"나는"** 금지. 종이 시험에 "기록 없음" 같은 안내를 쓰지 않는다 (표에서 조용히 뺀다).
6. **제목 · 소제목 · 표 머리 · 원인의 굵은 머리말 · head 는 명사구.** 소제목은 「틀린 문제 · 원인 · 보완 방법 · 예제 풀이 · 다시 풀기 · 연습 문제 · 정답과 해설」.
7. 표지 「푸는 순서」에는 목차와 순서만 — 설명을 붙이지 않는다. 날짜 박힌 안내(「9/30 보강 때 제출」)도 넣지 않는다.
8. 학생 배부 금지어 (하세요 · 판서 · 채점하면 · 학생이 · 배점 · 출제자) · 출제자 시각 금지. 우리말은 `공용/규칙/글쓰기.md` 적용 (이 자료는 적용 대상으로 지정됨).
9. 보완 방법의 예문·개념은 **그 반 시험 범위 원문에 있는 것만** — 다른 교재(첫단추 · 천일문 등)의 개념·예문을 가져오지 않는다.
10. 표 안에 긴 영어 문장을 넣으면 칸이 넓어진다 — 빌더가 막으면 문단으로 바꾼다.

## 5. 빌드 · 점검
```
py 공용/build/약점보완/build.py <반>/시험대비/<시험>/작업/개인패키지 이름 [이름…]
```
- 빌더가 3절 규칙 일부와 구조(오답 누락 · 표지 한 쪽 · 쪽 너비 · 금지 표현)를 막는다. 걸리면 고치고 다시.
- 글쓰기 검사: `공용/build/core/checks.py` 의 `writing_ko` 를 head · how · walk · habits · miss · why 에 돌린다 (표 머리·제목의 "것" 은 예외).
- 표지와 약점 한 장을 렌더해서 눈으로 본다.

## 6. 배부
- 문제편 + **답지 따로** (`_답지.pdf`). 사용자 결정(2026-09-29): **답지는 학생에게 주고 스스로 채점**한다. 학습 확인은 7절 확인 시험으로 한다.
- 그날 수업 폴더에 `4_숙제_약점보완자료_<이름>.pdf` · `_답지.pdf`, 다음 수업 폴더에 `2_숙제확인_…_답지.pdf`.
- 이미 인쇄·배부한 뒤에는 표지 형식을 바꾸지 않는다 (예: "그 밖의 유형" 줄 — 사용자가 유지 결정).

## 7. 약점 확인 시험 (사용자가 원할 때)
처음 보는 문항으로 약점이 고쳐졌는지 본다. **지문은 범위 그대로, 밑줄 · 빈칸 · 선택지는 기존 회차와 다르게** 새로 낸다.
1. 새 문항 모음을 만든다 — `작업/확인시험/bank_*.py` (1과·학평을 나눠 에이전트 병렬 가능). 반 `분석/출제경향.md` 출제 공식과 기존 출제 지침을 따른다.
2. 문항마다 `py 공용/build/약점보완/확인시험.py <폴더> --bank bank_X` (빌더 점검 결함 0) · `--dup` (기존 회차와 겹침 0).
3. **모든 문항을 직접 풀어 본다** — 정답 하나 · 근거가 지문 안 · 답이 둘로 갈릴 표적(예: was being 을 진행형으로 읽을 여지) 없음.
4. 학생별 `tests` 를 `설정.json` 에 쓴다 — 약점 보완 자료의 약점 순서대로 8~11문항.
   - **한 시험지 안에 같은 지문이 두 번 나오지 않게** (지문끼리 답을 흘린다).
   - 학생이 보완 자료 **예제로 이미 본 지문·유형 조합은 쓰지 않는다**.
5. `py 공용/build/약점보완/확인시험.py <폴더>` → 배부. 온라인 채점은 `온라인배포` 스킬 (`--id <반>_약점확인_<이름>`), 링크를 열어 제목을 확인하고 README 링크 절에 적는다.
6. 통과 기준은 **정하지 않는다** — 사용자가 정한다.

## 8. 기록
- 반 `CLAUDE.md` 「자료 위치」에 작업폴더 두 줄 · 수업일지에 배부·다음 할 일.
- 학생별 데이터가 늦게 오면(미제출 회차) 있는 기록으로 먼저 만들고, 빌더가 안 푼 회차를 연습 문제에서 빼는지 확인한다.

## 하지 말 것
- 초안을 검토 없이 내놓지 않는다.
- 새 약점 보완 자료에 새 문항을 만들지 않는다 (문항은 기존 회차 원문 그대로). 새 문항은 확인 시험에만.
- 커트라인·통과 기준을 임의로 정하지 않는다.
